# AGENTS.md

Инструкции для AI-агента (Google Jules). Источник требований: `SPEC.md`. Если инструкция расходится со SPEC, прав SPEC, а расхождение нужно указать в описании PR.

## Проект

Сервис регистрации на мероприятия: лимит мест, лист ожидания, билеты с кодом, чекин, live-счётчики, письма. Backend: Python 3.12 + FastAPI + SQLAlchemy 2 + Alembic. БД: PostgreSQL 16. Frontend: React + Vite. Почта: SMTP → MailHog.

## Структура

```
backend/app/        main.py, db.py, models.py, schemas.py, api/, services/, workers/
backend/tests/
backend/alembic/
frontend/src/
docker-compose.yml
SPEC.md  AGENTS.md  README.md  DEVLOG.md
docs/prompts/       промпты и решения (ведёт владелец репозитория)
```

## Команды

```
docker compose up --build            # весь стек
cd backend && pytest -q              # тесты (нужен PostgreSQL по DATABASE_URL)
cd backend && alembic upgrade head   # миграции
cd frontend && npm ci && npm run build
```

Если Docker в среде недоступен, поставь PostgreSQL через apt и задай `DATABASE_URL`. Тесты используют отдельную БД и не трогают рабочую.

## Правила работы

1. **Одна задача: один PR.** Задачи идут по этапам из SPEC §10. Не начинай следующий этап, пока не выполнен текущий.
2. **Тесты обязательны.** Код без теста на заявленное поведение не считается готовым. Для гонок пиши тесты с реальной параллельностью (несколько соединений), а не последовательные.
3. **Схема БД меняется только через Alembic-миграцию.** Не правь модели без миграции.
4. **Консистентность в БД, а не в приложении.** Лимит мест, дубли и чекин защищаются блокировкой, уникальным индексом или атомарным UPDATE (SPEC §5). Проверка «сначала SELECT, потом INSERT» без блокировки запрещена.
5. **Письма только через outbox** (`notifications`). Прямой вызов SMTP из обработчика запроса запрещён.
6. **SSE публикуется после commit,** не внутри транзакции.
7. **Время:** хранится в UTC (`timestamptz`), в коде используй aware-datetime.
8. **Email** нормализуется (trim + lower) в одном месте, в сервисном слое.
9. **Без секретов в репозитории.** Конфигурация через переменные окружения, пример в `.env.example`.
10. **Не выдумывай готовность.** В описании PR: что сделано, что проверено тестами, что не сделано. Если тест падает, скажи об этом, а не отключай его.
11. **Зависимости:** добавляй только нужные, фиксируй версии, коротко объясняй причину в описании PR.
12. **Не переписывай чужие файлы без нужды.** Правка должна быть минимальной для задачи.

## Коммиты и PR

- Коммиты мелкие, формат `тип: что сделано` (`feat`, `fix`, `test`, `docs`, `chore`).
- Описание PR: цель, что изменено, как проверить, результат `pytest`, известные ограничения.
- После каждого PR добавь запись в `DEVLOG.md`: дата и время (UTC), что сделано, какие решения приняты и почему.

## Критерии готовности (Definition of Done)

- `pytest -q` проходит локально, новые поведения покрыты тестами.
- `docker compose up --build` поднимает стек без ручных шагов.
- Миграции применяются на чистой БД.
- README и `DEVLOG.md` обновлены, если поведение или запуск изменились.
